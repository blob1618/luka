# Comparador de supermercados (HU-PRE-04 y HU-PRE-05)

## Fuente y alcance

La fuente primaria es el ZIP minorista diario de [SEPA / Precios Claros](https://www.argentina.gob.ar/economia/industria-y-comercio/defensadelconsumidor/precios-sepa). El catálogo oficial publica el enlace y la fecha del archivo; no ofrece una API oficial de búsqueda por producto. LUKA descarga el ZIP, lee los ZIP internos por comercio, conserva los EAN válidos de las provincias configuradas y publica un snapshot nuevo sólo cuando finaliza la carga. La consulta no descarga datos en tiempo real. Los precios se atribuyen a SEPA con fecha y sucursal, y no garantizan el precio en góndola.

El [catálogo oficial](https://datos.produccion.gob.ar/api/3/action/package_show?id=sepa-precios) declara licencia CC-BY-4.0; las respuestas muestran la fuente y la fecha del dato.

Si el API de metadatos responde 403 desde el alojamiento, Luka consulta las cabeceras de los siete [recursos ZIP semanales oficiales](https://datos.produccion.gob.ar/dataset/sepa-precios). En Render y GitHub Actions se observó 403 tanto para el catálogo como para los siete ZIP el 20/11/2026. En ese caso Luka consulta el [espejo del propio proyecto](https://github.com/blob1618/luka/releases/tag/sepa-feed). El workflow de GitHub Actions intenta primero descargar el ZIP oficial; si la fuente lo rechaza, usa la [copia archivada por catdevnull](https://github.com/catdevnull/sepa-precios-metadata) y comprueba en el archivo la fecha, el ID y la revisión del recurso, y la URL oficial. Esa copia depende de un tercero y la comprobación de metadatos no equivale a una firma del organismo oficial. El workflow conserva sólo las sucursales y precios de AR-H, publica primero ese ZIP compacto y después un manifiesto con fecha, URL oficial de origen, cobertura, tamaño y SHA-256. Luka exige fecha de hasta tres días y verifica el SHA-256 antes de procesar el ZIP. Si no hay una copia fresca y verificable o falla la descarga, informa indisponibilidad sin inventar precios.

El contrato interno usa EAN, descripción, marca, presentación, sucursal, localidad, provincia, fecha informada por comercio, precio de lista y promociones con sus leyendas. La persona busca por nombre; cuando hay varias coincidencias, Luka le pide marca o presentación y nunca le exige el código interno. El ahorro entre sucursales se calcula para el mismo EAN, presentación y fecha informada, con la referencia mostrada. Sólo se aplica la promoción general (`promo1`) cuando se puede comprobar que su vigencia incluye el día de la consulta y la leyenda no exige varias unidades ni condiciones personales o de pago. La promoción condicionada (`promo2`) no se presenta como una oferta universal. Un producto faltante se informa sin imputar un precio. Si el último snapshot tiene más de dos días, la consulta informa indisponibilidad.

La persona pide productos por nombre, por ejemplo «quiero poner arroz en mi canasta». Luka busca en SEPA para su localidad y, si hay varias presentaciones, usa el LLM para seleccionar nombres que correspondan al producto pedido, sin reglas específicas para alimentos concretos. El LLM sólo recibe el pedido y los nombres; el backend conserva los identificadores y precios. Se muestran hasta cinco presentaciones ordenadas por el menor precio del paquete, cada una con ese precio, comercio y sucursal. Si el modelo no puede distinguir el producto o falla, Luka pide tipo, marca o presentación. Es una selección probabilística: la persona elige la presentación antes de que se prepare la propuesta. El EAN queda como identificador interno y nunca es un dato exigido al usuario. Si falta la localidad, la pregunta antes de buscar. La canasta frecuente se guarda por usuario con EAN interno, cantidad y localidad/provincia. Agregar o reemplazarla requiere una propuesta completa y una confirmación posterior. Al mostrar la canasta, Luka ofrece «Comparar precios» y «Consultar ofertas»; también acepta pedidos de ofertas por texto en cualquier momento. Son lecturas independientes de los límites presupuestarios y no crean movimientos ni cambian presupuestos. La alerta del 80 % sólo informa sobre el presupuesto.

## Configuración y operación

1. Aplicar `supabase/migrations/20261119190000_supermarket_prices.sql` y `supabase/migrations/20261119193000_shopping_basket.sql` mediante el proceso de migraciones del proyecto. No ejecutar cambios de esquema manuales sobre Supabase.
2. Medir espacio, tiempo de descarga y carga en el entorno previsto. El ZIP oficial ronda los 320–340 MB comprimidos; el ZIP compacto de AR-H del 19/11/2026 ocupó 1,76 MB. La base indexada puede ocupar bastante más. Evaluar capacidad antes de ampliar cobertura.
3. Configurar `SEPA_PROVINCES` con códigos de provincia separados por comas, por ejemplo `AR-H`, y `SEPA_INGEST_ENABLED=1`. Sin provincias configuradas, la ingesta se niega a iniciar. El backend puede responder «sin precios cargados» hasta que se complete la primera carga.
4. El [workflow de espejo](../.github/workflows/sepa-mirror.yml) corre a las 19:00 UTC y puede lanzarse manualmente desde Actions. Requiere permiso `contents: write` para actualizar la release pública `sepa-feed`; no requiere secretos de producción. Si GitHub Actions tampoco puede consultar el origen oficial, recurre al archivo histórico fechado y valida sus metadatos oficiales incorporados. Si tampoco está disponible o es antiguo, falla y conserva el último manifiesto.
5. Al iniciar el servicio con la ingesta habilitada y sin un snapshot listo, Luka programa la primera carga para un minuto después. La tarea diaria se programa a las 17:30 de Argentina, después de la publicación del espejo. Debe correr en un único worker, como el scheduler actual. Para un reintento manual en un entorno con consola, ejecutar `python -m scripts.ingest_sepa` dentro del contenedor con la configuración del servicio.
6. Revisar `sepa_ingest_ready` (fecha, filas, descartes) o `sepa_ingest_failed` en los logs. La conexión PostgreSQL deshabilita los prepared statements de Psycopg para el pooler transaccional de Supabase. Si falla la descarga o carga, el snapshot anterior permanece disponible sólo dentro de la ventana de dos días. Los lectores nunca usan filas de una carga incompleta. El reintento manual vuelve a descargar el archivo. Redis guarda cada comparación durante 30 minutos con el ID del snapshot en la clave; publicar uno nuevo invalida lógicamente las claves anteriores.

Los tests de ingesta usan ZIP/CSV contractuales pequeños y no descargan el archivo real de cientos de MB. Antes de habilitar el servicio para usuarios finales, confirmar capacidad de base y almacenamiento, probar una carga real en staging, verificar la licencia aplicable y atribución de los datos, y validar las respuestas desde WhatsApp real. CI, simulador y migración versionada no prueban esos pasos.
